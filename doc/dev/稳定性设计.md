# 稳定性设计:远程桌面链路 与 升级链路

> 本文记录这两条「命脉链路」的**现行设计、每个决策背后的原因、以及故意不做的事**。
> 改动这两条链路前必读;若要推翻某个决策,先读懂它对应的学费(见 [P0复盘.md](P0复盘.md))。
> 通用不变式见 [架构守则.md](架构守则.md),发版检查见 [发布门禁.md](发布门禁.md)。

## 一、远程桌面链路

```
浏览器(noVNC iframe) ──ws──> 面板(http-proxy, 注入凭据) ──ws──> 实例容器 nginx:3000 ──> websockify ──> Xvnc(KasmVNC)
```

### 关键设计决策(为什么是现在这样)

| 决策 | 原因 |
|---|---|
| **重连一律整页重载**,绝不页内重挂 iframe | 新旧两条 ws 短暂并存会概率性把 Xvnc 卡死(需重启容器才能恢复)。修过 4 次卡死后确立(`13ec0bd→b0511f5`),**不要退回去** |
| **502 返回自动重连页**(3s×10 次→手动重试) | 纯文本 502 会被 iframe 判为"已加载",用户卡在黑屏死页。实例重启/升级/自愈期间的短暂不可用应自动恢复 |
| **代理双侧 TCP keepalive(30s)** | 客户端断网/切网(WiFi→4G、NAS 休眠)时 TCP 不会通知,半开死连接可挂数小时,对 KasmVNC 是幽灵会话占坑——与新连接并存正是 Xvnc 卡死诱因 |
| **看门狗 soft/hard 双阈值内存自愈** | KasmVNC/Xvnc 长跑泄漏(实测 24h 可到 ~9GiB)。soft(默认 1500MB)只在无活跃会话时柔和重启;hard(默认 2500MB)无条件重启防 OOM |
| **VNC 响应性探测默认关闭** | 宿主级 CPU/IO 争用(如同机 docker build)会让探测超时、误杀健康实例。需要时 `WOC_WATCHDOG_HEALTH_FAILS=N` 开启 |
| **用户自助「卡死自愈」+ 3 分钟限流** | Xvnc ws 接收器卡死时 nginx 仍能出静态页(看起来在线),只有重启容器能救;限流防重启风暴 |
| **`[vnc]` 三段连接日志**(尝试/上游101/关闭时长) | 与容器内 KasmVNC 日志按时间对齐,可判定卡在"面板→实例"还是实例内部 |
| **控制权心跳(2.5s 节流)** | 兼做"是否有人在用"信号,供 soft 自愈决定时机 |
| **X 环境:xsettingsd `Xft/DPI 98304`** | XSETTINGS 单位是 DPI×1024;写错 = 所有 Chromium 内核(微信 CEF)GPU 崩溃(史上最大 P0,见复盘) |
| **Chromium 从 snapshot.debian.org 锚定版本** | Debian 源只留最新版,新版在本栈上反复致命崩溃(149 断言收紧、150 非首跑必崩)。升级 = 显式改 Dockerfile 里的快照时间戳+版本号并过全套门禁(`scripts/bump-chromium.py` 自动找 bookworm 最新构建和双架构都齐的快照,`--check` 只看落后多少) |
| **面板↔实例镜像版本耦合** | 正式版面板把实例镜像 `:latest` 改写为与自身相同的版本 tag,同版本一起验证、一起发布;杜绝旧面板×新实例的未验证组合 |
| **往 iframe 挂监听的 effect 按「加载代次」`frameGen` 重挂** | iframe 会在页内自行换文档(实例短暂不可用时反代先回自动重连页,3s 后 reload 进 noVNC)。只依赖 `frameLoaded` 的 effect 此时不会重跑,监听留在已销毁的旧文档上 → 无感输入打的中文被吞(只剩英文)、粘贴桥/控制权心跳静默失效。新增此类 effect 必须依赖 `frameGen` |
| **无感输入:落到 canvas 的焦点立刻交还给 `noVNC_keyboardinput`** | KasmVNC 在 iframe 里不拦 canvas 上 mousedown 的默认聚焦(只在顶层页面才拦)。隐藏输入框一旦失焦,之后每次点画面焦点都落到 canvas → 浏览器停用本机输入法(候选框消失、只能打英文),且再也回不去,只能刷新 |
| **扩展报错在捕获阶段截下;关误报浮层须清空内容** | KasmVNC 的全局错误处理器只展示第一条错误(内容非空就不再弹)。关浮层不清空 → 之后 KasmVNC 真崩溃也不弹浮层,致命自愈整页失效,桌面停在断开状态 |
| **断线重连空档的 `lastActiveAt` 报错视为无害,只在 `disconnected` 时整页重连** | KasmVNC 的保活定时器在 `UI.rfb` 被置空的重连空档里必抛这个错(每次重连还多叠一个定时器)。干净断开后 noVNC 已排好 2s 自带重连,若当致命错误整页重载,每次网络抖动都多一次整页重连并消耗「5 分钟 4 次」的自愈额度(实测 6 次干净断线 3 次被拖成整页重载);只有停在 `disconnected`(非干净断开,noVNC 不会再自己重连)才需要整页重连 |
| **服务端「卡死」识别 + 自愈:真实请求 25s 无应答,10 分钟 2 次 → 重启实例** | 卡死的 KasmVNC 静态页照常能出(kclient),只有 websocket 升级永远不回 101,旧的 HTTP 周期探测看不到;noVNC 也没有连接超时,会一直「连接中」。用真实用户请求判定:快速失败(实例刚起、502/拒绝连接)不计数,只计「25s 毫无响应」;容器须已运行满 3 分钟、15 分钟冷却、沿用当前镜像(R10)。与被撤掉的客户端 heal 不同:信号来自实例对升级请求的直接响应,不受客户端网络、后台标签页、预热期影响。`WOC_STUCK_HEAL=0` 关闭自动重启。另有两种同样判卡死:升级回了 101 却 25s 没有任何数据(KasmVNC 的 websocket 握手由单独线程完成,主循环卡住时照样回 101,健康实例几毫秒内就发来 RFB 版本号);过了预热期还接连快速失败(3 分钟内 4 次 502/拒绝连接 = Xvnc 没在运行,见下一条) |
| **实例启动时清掉残留的 X 显示锁(`03-woc-xlock`)** | 宿主断电、NAS 强制重启、Docker 被强杀时 Xvnc 来不及删 `/tmp/.X1-lock`,容器原样再起时文件还在。Xvnc 按锁里的进程号判断显示是否被占用,新容器里这个号恰好被别的进程用上(实测是 nginx、s6 服务脚本)就认定 :1 已有 X 服务器、退出,s6 反复拉起反复失败,桌面永远「连接中」(实测强杀 Docker 后 11 个实例里 2 个这样)。启动钩子在任何服务起来前删掉;老镜像没有这个钩子,靠服务端「快速失败」判定重建容器 |
| **面板按 mountinfo 里的容器 ID 认出自己,实例接到面板所在的自定义网络(不选默认 bridge)** | 反代按容器名访问实例,实例必须和面板同在一个自定义网络。旧逻辑按 hostname / 固定名 `woc-panel` 找自己、取排序后第一个网络:自定义 hostname + 改了容器名(或被 1Panel/Portainer 重建时复刻旧 Hostname)就找不到自己,面板同时挂着 bridge 且另一网络名排在 bridge 之后就选中 bridge,两种都把实例建到 bridge → 502(#103)。启动时对「与面板不同网」的实例只记日志、不自动重建(用户点「重启」即恢复);`WOC_DOCKER_NETWORK` 可显式指定。现在默认用实例专用网络 `woc-instances`(面板建网并以 `GwPriority=-1` 接入,不抢默认网关/端口映射;面板容器被外部重建丢了这个网络时,启动时与每 2 分钟复查都会接回;建不起来则退回面板所在网络并记日志)。启动流程先等 Docker 就绪(最多 30 秒):socket-proxy 加固部署下宿主重启 / 同时重建时代理常晚几秒,不等的话接不上专用网络,迁过去的实例桌面 502 直到下次复查;`ensureRunning` 也只在容器 404 时才重建,Docker 一时连不上不当成「容器不存在」;自更新重建面板时主网络取 `HostConfig.NetworkMode`,不按名字排序取第一个 |
| **打字借用容器剪贴板,打完归还;借用的内容不同步回本机** | `/type` 靠「写容器剪贴板 + Ctrl+V」把字贴进应用(绕开 KasmVNC 的 keysym 容量上限),副作用是容器剪贴板被换成刚打的字,KasmVNC 的无缝剪贴板再把它写进用户本机剪贴板(实测:本机复制链接 → 进桌面打字 → Ctrl+V 贴出刚打的字,链接没了)。服务端一轮打字的第一段先存下原内容(图片 > 文件列表 > 文字,应用私有格式还原不了),打完 1 秒且剪贴板仍是我们放的字才放回;经面板的 Ctrl+V 先归还再粘;前端对「借用内容 / 归还的原内容」不写本机剪贴板 |
| **Ctrl+V 时本机剪贴板更新,就贴本机的** | KasmVNC 只在「窗口重新获得焦点后第一次点画面」时把本机剪贴板推上去,切回来直接 Ctrl+V 粘到的是容器旧内容;局域网 http 下浏览器不给剪贴板 API,根本不同步。粘贴桥比对本机剪贴板与容器里用户自己的内容,本机新就经 `/paste-text` 贴本机文字;应用内复制、应用内粘贴仍走容器原生 Ctrl+V,保留应用自己的格式 |
| **不经合成直接插入的文字也进有序队列** | 全角标点、系统表情面板、语音输入不走 composition,noVNC 按 keysym 发:非 ASCII 要临时映射键码(实测丢字),且经 websocket 抢在走 HTTP 转发的中文前面(实测依次输入「你好」「，」「世界」「。」,远端收到「。你好世界」)。在 beforeinput 截下,与中文同一队列 |
| **中文转发期间,会直接发 keysym 的按键都进有序队列** | KasmVNC 在输入法模式下只把 keyCode 229 和数字当输入法按键,空格、英文状态下的字母和标点、回车、退格、方向键都直接发 keysym,经 websocket 抢在走 HTTP 转发的中文前面:拼音上屏后连点空格,远端成了「   你好」(#155),「你好」后紧跟 Backspace、方向键会作用在错的位置。队列忙时截下这些键:可见字符并进待发文字(一句英文合成一次转发),编辑键按键名发且带上 Shift(微信里 Shift+回车是换行,此前被当成回车直接把消息发了出去)。keyCode 229 的键一律不碰——那是输入法在处理,包括下一个词的拼音首字母,抢走就成了「你好y呀」 |

### 故意不做的事(反复想清楚了)

- **"新连接踢掉旧连接"(单会话强制)**:noVNC 开着 `reconnect=true`,两台设备会互踢打架(PC 重连踢手机、手机重连踢 PC,无限战争)。整页重载 + keepalive 已覆盖主要场景。
- **页内软重连**:见上,双 ws 并存卡死 Xvnc。
- **激进的健康探测**:误杀比漏杀更伤(用户正用着被重启)。

### 已知单点(接受的风险)

链路可用性 = KasmVNC 单进程可用性:Xvnc 卡死无法进程内恢复,只能重启容器。缓解 = 服务端卡死识别自动重启 + 用户自助「重启」+ 看门狗;根治需换流媒体栈(selkies/WebRTC),收益不抵风险,暂不做。

卡死的触发条件仍未坐实。群里反馈「经常切换实例,微信就死了要重启」:用真实微信 4.1(未登录扫码页)在侧栏里快速来回切 5 个实例(含未安装的,切过去会卸掉 iframe)约 170 轮,每轮 3~8 次、每次停 0.15~2.5s,没复现;Xvnc 123 次连接后内存仍是 79MB 左右,不泄漏。已排除:对实例做过 100~150 次一组的「异常断开 / 升级后立即断开 / 握手中途断开 / 卡在握手不说话(40 条挂着)/ 握手后停止读取(12 条挂着)/ 新旧连接交替」压测,以及一个客户端冻结 60s 期间另一客户端接入,KasmVNC 都能继续接受新连接;每条连接约占 3 个 fd + 1 个线程,关闭后回收。模拟卡死用 `kill -STOP` 冻结 Xvnc:静态页 20ms 返回、ws 升级无任何响应,与现场描述一致。

## 二、升级链路(三条)

### 共同不变式

1. **恢复类操作幂等(R10)**:重启/卡死自愈/看门狗自愈/重置设备ID 一律 `runInstance(inst, { keepImage: true })`——沿用当前镜像重建,绝不因本地 `:latest` 被拉新过就隐式换版。换镜像**只**发生在显式「升级」。容器在用的镜像可能已经不在本机:Docker 29 默认的 containerd 镜像存储里,同名 tag 一旦指向新镜像(重新拉取、本地重建同名镜像),旧镜像当场消失,用它跑着的容器照常在跑。这时没法沿用它重建,改为**原地重启**容器(先清 X 显示锁),绝不先删后建——实测先删后建会报 No such image,实例只剩数据卷。
2. **长任务异步(R4)**:凡内部含拉镜像的接口,立即返回 + 后台执行 + 轮询进度。同步等待会被反代 ~60s 掐断 → 误报失败 → 用户重试 → 并发重建。
3. **资源有界(R3)**:实例容器建时注入 `LogConfig 20m×2`;升级完成回收悬空镜像;拉取带 5 分钟无进度停滞超时(`WOC_PULL_STALL_MIN`)。
4. **先备好镜像,再删旧容器**:`runInstance` 先确认目标镜像在本地(必要时拉取),成功后才删旧容器重建。此前先删后拉,面板刚更新、本地只有旧版本号的镜像、网络又不通时点「升级实例」,旧容器删了新容器建不出来,实例直接没了(已实测)。拉取失败且本地目标镜像就是当前镜像时不重建,直接报「未升级」,免得白白重启一次。

### ① 面板自更新(watchtower 式)

流程:拉新镜像(带停滞超时)→ 派生 helper 容器(新镜像+docker.sock)→ helper 停删旧面板 → 按**声明式配置**重建(env = 新镜像 baked + compose 运行时差量;**绝不克隆旧容器的 Hostname 等运行时值**,那是 v1.2.6 全员 502 的根因)→ 健康检查稳定 8s → 成功;失败自动回滚旧镜像。

- **版本锚定(R1)**:优先拉「更新检查」宣告的具体版本 tag(如 `1.3.1`),失败回退 `:latest`——保证"更新到 v1.3.1"拿到的就是 v1.3.1。
- `updateInFlight` 10 分钟自动复位(helper 静默失败后用户可重试)。
- 最坏兜底:helper 也挂 → 用户 `docker compose up -d` 即恢复。

### ② 单实例升级

`POST /instances/:id/upgrade` → 登记 `upgradingIds` 立即返回 → 后台 拉取→重建(保留数据卷)→ 移出登记。前端轮询 `upgrade-status.upgradingIds`,按"升级后是否仍落后"给结论。与一键升级互斥(409)。**保留原运行状态**:原本停止的实例升级后停回去。

### ③ 一键升级全部

顺序必须是:**先拉镜像 → 再判定落后清单 → 逐个重建**(反过来会漏掉"本来等于旧最新版"的实例)。镜像只拉一次;进度(`n/total · 当前实例`)从 `upgrade-status.upgradeAll` 轮询;页面刷新后自动恢复轮询;完成后回收悬空镜像。

### 「可升级」检测(双信号)

- **本地信号**:容器镜像 id ≠ 本地 `:latest` id(逐实例,驱动"可升级"角标)。
- **远端信号**:registry manifest **HEAD** digest ≠ 本地 RepoDigests(30 分钟缓存、后台刷新、离线/自构建返回未知不打扰)。**没有它,用户更新完面板后本地镜像还是旧的,升级引导永远不出现**(设计盲区,已踩过)。

### 用户心智:更新面板 ≠ 更新实例

二者是不同镜像/容器。所有涉及实例镜像的修复,发布说明必须显式提示"请升级实例";面板在「关于」与「管理」两处主动提示落后实例数。
