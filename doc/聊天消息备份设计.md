# 微信 / QQ 聊天消息备份（全量 + 增量）设计

## 目标与边界

给每个实例提供「聊天数据」级别的备份，而非整卷备份（整卷含程序本体、core dump、缓存，6GB+，浪费）。只备份真正承载聊天记录与恢复所需的最小文件集。

- **微信实例**（`appType=wechat`）：`/config/xwechat_files`（4.1G）、`/config/.xwechat`（723M，运行时/索引）、`/config/.woc-machine-id`（解密环境绑定 key）、`/config/Desktop`（收到的文件 71M）。
- **QQ 实例**（`appType=qq`）：`/config/.config/QQ`（约 600M，含 `nt_db/nt_msg.db` 等消息库）。
- 不备份：`wechat/`/`qq/` 程序本体（可从镜像重装）、`core`（崩溃 dump）、`.cache`、`chromium`。

## 关键约束（决定实现方式）

1. **聊天库是 SQLCipher 加密的**（微信 `message_0.db` 文件头 `22 fe 3d f8...`，标准 sqlite3 打不开）。所以：
   - 不能用 `sqlite3.Connection.backup()` 在线热备（打不开库）；
   - 备份产物 = 原样文件，**不能直接阅读**，只能恢复到同一 WOC 环境（靠 `.woc-machine-id` 解密）。
2. **一致性靠文件级协调，不靠 DB API**：SQLite WAL 模式下，`db` + `db-wal` + `db-shm` 需同一时刻快照。策略=「冻结应用进程」：备份前对应用主进程发 `SIGSTOP`（停止写库，快照一致；且不会像 pkill 那样触发 autostart 重启），打包后 `SIGCONT` 恢复。容器全程运行（docker exec 需要容器 running），只让应用有几秒不可操作。
   - **关键安全约束**：必须用 `pkill -STOP -x <精确 comm 名>`，绝不能用 `-f`——`-f` 匹配整条命令行，会命中执行该命令的 `sh` 自身（其命令行里含进程名字符串），把自己冻住。实测踩过这个坑。解冻放在 `finally`，任何异常都保证恢复，绝不把用户微信留在冻结态。
3. **增量以文件为粒度**：加密库无法做页级/记录级差异，增量 = mtime + size 变化的文件。微信库整体重写频繁（message_0.db 60MB 秒级变动），但图片/语音/视频等资源文件大而稳定，增量主要省在资源文件上。

## 备份产物布局

面板容器内（挂 `data-panel` 卷，宿主 `./data-panel`），按实例分目录：

```
/data/chat-backups/<instId>/
  chain.json                       # 本实例的备份链元数据（基线 + 增量序列）
  full-<YYYYMMDD-HHmmss>.tar.gz    # 全量基线
  inc-<YYYYMMDD-HHmmss>.tar.gz     # 增量（相对上一个 full/inc）
```

`chain.json` 示例：

```json
{
  "version": 1,
  "appType": "wechat",
  "entries": [
    { "id": "full-20261120-220000", "kind": "full", "file": "full-....tar.gz",
      "createdAt": 173..., "bytes": 4831838208, "fileCount": 24367,
      "map": { "xwechat_files/.../message_0.db": [mtimeSec, size], ... } },
    { "id": "inc-20261121-020000", "kind": "inc", "base": "full-20261120-220000",
      "file": "inc-....tar.gz", "createdAt": ..., "bytes": 52428800,
      "fileCount": 12, "map": { ...全量快照... } }
  ]
}
```

- 每个 `map` 是该备份完成后聊天文件集的完整 `{相对路径: [mtime秒, size]}` 快照，用于下一次增量比对、以及恢复链校验。
- 增量包只含相对上一个 entry 变化/新增的文件；删除的文件在 `chain.json` 里标记（恢复时按需删除，见下）。

## 备份流程（每次全量/增量共用）

1. 管理员鉴权 + 实例存在校验 + `chatBusy` 防并发。实例必须处于 running（docker exec 需要）。
2. **冻结应用**：`pkill -STOP -x wechat`（QQ 为 `qq`）→ 应用停写、快照一致、不触发 autostart；返回解冻闭包，`finally` 必调。
3. **枚举**聊天文件：容器内 `find` 目标目录，`-printf '%p\t%T@\t%s'` 得到 `{path, mtime, size}`。
4. **比对**（增量时）：读 `chain.json` 最后一个 entry 的 `map`，筛出 mtime 或 size 变化、以及新增的文件；全量则取全部。
5. **打包**：`docker exec` 里 `tar -czf - -C /config -- <相对路径列表>`，通过 hijack 流 + 手写帧解析流式写入面板本地文件（复用 `downloadAllFromInstance` 的帧解析背压范式，不整包入内存）。文件列表很长时写入容器临时文件用 `tar -T`。
6. **写 manifest**：原子写 `chain.json`（tmp + rename）。
7. **恢复应用**：`finally` 里 `pkill -CONT -x`，任何失败都保证解冻（绝不把用户应用留在冻结态）。容器全程运行，无需重启实例。
8. 返回任务结果（走 `VolJob` 风格的后台 `chatJobs`，前端轮询进度）。

## 恢复

- **全量恢复**：选任一条 full，解包到 `/config`（复用 `volRestoreArchive` 的解包 + 停/启逻辑），因条目前缀是聊天子目录，直接解到 `/config` 根即可覆盖回去。
- **增量恢复**：选目标 entry，从它所属的 full 开始，按 chain 顺序依次解包每个 inc；每个 inc 解包前按 `map` 差异删除「已被删除的文件」（首次实现可先提示用户手动清理，避免误删）。
- 恢复同样先停实例、后启动，与重启/升级共用生命周期锁。

## 定时增量（可选）

- 复用 `setInterval().unref()` 范式（见 `version.ts` / watchdog）。开关与间隔走环境变量：`WOC_CHAT_BACKUP_AUTO=1`、`WOC_CHAT_BACKUP_CRON_MIN=360`（分钟间隔）、`WOC_CHAT_BACKUP_KEEP=7`（保留最近 N 条）。默认关闭，避免未配置就停服。
- 定时器触发静默增量；全量只手动触发（或首次自动建基线）。
- 保留策略：`WOC_CHAT_BACKUP_KEEP=N` = 额外保留 N 个「旧轮次」条目（默认 0 = 只保留当前轮次）。**绝不删最后一个 full 基线及其后的增量**，避免基线被删导致增量链失效。一轮 = 一个 full + 其后直到下一个 full 前的全部 inc。

## API（管理员）

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/admin/instances/:id/chat-backup` | body `{mode:'full'\|'inc'}` 触发备份，返回任务号 |
| GET | `/api/admin/instances/:id/chat-backup/jobs/:job` | 轮询进度 |
| GET | `/api/admin/instances/:id/chat-backup` | 列出备份链 |
| GET | `/api/admin/instances/:id/chat-backup/:entryId/download` | 下载某个备份包 |
| DELETE | `/api/admin/instances/:id/chat-backup/:entryId` | 删除某个备份（含文件与 chain 记录） |
| POST | `/api/admin/instances/:id/chat-backup/:entryId/restore` | 恢复到该 entry（后台任务） |

## 安全

- 所有端点 `requireAdmin`（备份含完整聊天数据，等同凭据）。
- 路径拼接只用语料白名单（instId 来自 `findInstance`、entryId 来自 chain），禁止 `..`；entryId 生成为固定格式。
- 下载走 `content-disposition` attachment，文件名 encodeURIComponent。
